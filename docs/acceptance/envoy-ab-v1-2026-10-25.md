# Envoy 固定评测集 v1：A/B 实测记录

- run_id：`envoy-ab-20261025-ff0ae997d591`
- 执行日期：2026-10-25（本地时区 +08:00）
- 模型：`anthropic/DeepSeek-V4.1-Flash`（经本机 LiteLLM 网关 `127.0.0.1:14050`，服务端账本读 `litellm` 库）
- 固定集：`benchmarks/fixed-set-v1`，20 个 package × 3 个 role × 2 臂 = 120 轮
- 产物：`artifacts/envoy-ab-v1/`（`summary.md`、`four-questions.md`、`summary.json`），由 `benchmarks/fixed-set-v1/verify_ab.sh` 从各 shard 一次性重算；评级只用终端答案，**不含** transcript 回收文本（`grade.jsonl` 每行 `answer_source` 均为 `terminal`）
- 一句话：**两臂墙钟上限不同（900 s vs 2400 s），所以这是探索性观察，不是同预算对照。** 在这个前提下：envoy 臂 60/60 轮在自身上限内退出，baseline 19/60；envoy 的输入 token 约为 baseline 的 3.8 倍（合计口径）。

## 1. 实验设计

| 项目 | baseline（对照） | envoy（处理） |
|---|---|---|
| 插件 | 不安装 Envoy | 安装 Envoy MCP 插件 |
| 每轮墙钟上限 | **900 s**（计划值） | **2400 s**（run-log 记录） |
| 其余条件 | 同一固定集、同一模型、同一 gateway、同一沙箱、同一提示词模板；两臂子进程都强制 `ENVOY_VISIBLE_BROWSER=0` | 同左 |
| 失败处理 | 撞上限记 `blocked(124)`；基础设施错误（`ConnectionRefused`）用 `--retry-capped` 重跑，不进报告 | 同左 |

上限不对称是**刻意接受的不完美设计**，不是可以忽略的细节：Envoy 的主张是「把原本做不到的长任务做完」，但这一轮没有在同一预算下重跑，所以完成率、墙钟、facts 三处差异都同时包含了「工具」和「多 2.7 倍时间」两个因素。凡引用这些数字，必须连带这句限制。

缓存隔离：`cache_read_input_tokens` 全为 0，账本口径 `verified_disabled`；两臂请求都带 salt 与会话标识，门禁校验 `server_ids_unique`、`every_request_has_metadata`。

## 2. 完成度与速度

| 臂 | 轮次 | completed（进程退出，非质量） | blocked(124) | failed | 墙钟中位 s | 墙钟 p90 s | 墙钟最大 s |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline | 60 | 19 | 41 | 0 | 900.0 | 900.1 | 900.2 |
| envoy | 60 | **60** | 0 | 0 | **255.7** | 884.6 | 2249.3 |

- baseline 的墙钟中位 900.0 s 是**撞上限的产物**，不是它「本来需要 900 s」；只有 19 轮真实跑完。
- envoy 的墙钟中位（255.7 s）远低于自身上限（2400 s），最慢一轮 2249.3 s 逼近上限。
- 首次证据中位：baseline 88.0 s（n=26）、envoy 48.4 s（n=30）。分母是「观测到证据的轮次」，两臂不同，只能作方向参考。
- 工具调用合计 261 vs 291；每轮工具调用中位 0.0 vs 0.5；同一 URL 在一次任务内被重复抓取合计 8 vs 2 次。

## 3. 信息量与质量（机械口径，均非正确性判定）

| 指标 | baseline | envoy |
|---|---:|---:|
| facts 命中 / 总数（阈值 0.6 词覆盖） | 47/516 = 9.1% | **197/516 = 38.2%** |
| 至少有 1 条 fact 命中的轮次 | 14/60 | **49/60** |
| 文章级引用命中（同文章规范化 URL） | **10** | 6 |
| host 级归属（诊断，不计作引用） | 12 | 25 |
| 终端答案中位字符（非空） | 3,125 | 8,142 |
| 空答案（`answer_chars==0`） | 31 | 0 |

读法与限制：

- facts 总数 516 = 20 个 package 各自声明的事实 × 3 个 role **重复计数**，不是 516 条唯一事实；命中标准是 claim 的英文特征词覆盖率 ≥ 0.6，只证明「答案里出现了这些词」，不证明结论正确。
- 文章级引用命中要求答案里出现与声明来源同一篇文章的规范化 URL；host 级归属只说明提到了该 host，所以两列分开，不合并成「来源命中」。
- baseline 的 31 条空答案来自 41 条撞上限的轮次，不是「答不出来」，因此 facts 9.1% 与 envoy 38.2% 的差距里混着「有没有机会产出答案」这一层，不能单独归因给 Envoy 的内容质量。
- 引用一列 baseline 反而更高（10 vs 6），本轮不做解释，也不拿它当 Envoy 的优势。
- `review.json` 未填：**没有任何一轮做过人工质量评审，`verified = 0`。** 本报告不回答「谁的答案更正确、更够用」。

## 4. 成本（服务端账本口径，含重试）

| 臂 | 计入请求 | 输入 token 合计 | 输入中位 | 输出 token 合计 |
|---|---:|---:|---:|---:|
| baseline | 834 | 25,733,603 | 216,678 | 472,107 |
| envoy | 2,915 | 98,689,702 | 804,922 | 2,827,612 |

- 合计口径：envoy 输入 token 是 baseline 的 3.8 倍，输出 6.0 倍。
- 两臂都 completed 且两侧账本非零的 17 对：envoy 输入 token 相对变化中位数 **+266.5%**（正数 = envoy 更贵）。
- 两臂都 completed 的 19 对账本 input 合计：2,904,111 → 17,422,152，envoy 是 baseline 的 6.0 倍。
- 两种口径的分母不同（合计 vs 中位；19 对 vs 17 对），不要混用。

**不宣称节省 token。** Envoy 更贵，因为它在真的读页面/视频内容（帧、转录、结构化证据），而这些正是 baseline 撞上限时没拿到的部分。可辩护的说法只有：在这套不同上限的设置里，Envoy 臂的进程完成数、facts 词覆盖、答案长度更高，同时成本显著更高。

## 7. 这一轮能得出与不能得出的结论

能得出（在上述限制内）：

- 在这套上限设置下，需要真实页面/视频内容的长任务里，baseline 900 s 内完成 19/60，Envoy 2400 s 内完成 60/60，且 Envoy 的墙钟中位远低于自身上限（255.7 s vs 2400 s），说明它并非全靠耗尽时间完成。
- 两臂都产出了终端答案的轮次里，Envoy 的 facts 词覆盖更高（197/516 vs 47/516）、答案更长，但这是机械匹配，不是正确性。
- 成本显著更高（合计输入 3.8 倍、输出 6.0 倍）；不得表述为 token 节省。

不能得出：

- 不能说「同预算下 Envoy 完成率更高」——上限不同，这一轮没有做同预算重跑。
- 不能给出人工质量优劣（`review.json` 未填，`verified = 0`）。
- 不能把 `suspect_complete`（13 vs 55）当作「答案正确」；它只是关键词规则下的疑似完成。
- 不能外推到固定集以外的站点或任务分布（n=60 轮/臂，站点以微信、B 站、小红书、抖音为主）。
